# Final Localhost Security Regression Test Plan

**Project:** `loyalty_managements`  
**Canonical local base URL:** `http://localhost/loyalty_managements`  
**Scope:** Manual regression of the active project tree. This plan does not change application behavior.

## Evidence Labels

- **CODE REVIEW VERIFIED:** Confirmed by reading active source in this workspace; not a claim that the browser test passed.
- **SYNTAX VERIFIED:** PHP lint passed for the listed files in the prior validation run. This does not prove runtime behavior.
- **MANUAL TEST REQUIRED:** Must be executed in the local browser. `Actual result` and `Status` remain blank until then.
- **RUNTIME VERIFIED:** Reserved for behavior actually exercised against localhost. Only a read-only reachability probe was run in this task; no authentication, remittance, or proof-view workflow was exercised.

## Before Testing

1. Use a disposable local database or take a restorable database backup. Do not run destructive, financial, or lockout tests against production or live customer data.
2. Use one normal browser profile for multi-tab/device-cookie tests. Do not use Incognito, another browser profile, or clear cookies between steps; those create a different `lm_device` identity.
3. Prepare test accounts: Admin A/B, Staff A/B, Customer A/B, Rider A/B. Keep credentials and OTPs local. Never paste or report passwords, OTPs, JWTs, session IDs, or cookie values.
4. Prepare disposable fixtures: Customer A/B orders and addresses; a completed Customer A order for review; a redemption and notifications/messages for both customers; one delivery assigned exclusively to Rider A and another to Rider B; one eligible completed COD order for remittance; test products and shop payment settings.
5. Use PayMongo sandbox only. For manual-payment tests use clearly fake test orders/receipts and do not represent them as real transfers. Record fixture IDs locally and restore/reset them after testing.
6. `ADMIN_AUTH_ENABLED` must be enabled for protected-page/API tests. In local configuration it may be disabled; production forces it on. Restore the original local setting after tests.
7. Keep DevTools Network open when testing APIs. Do not copy response bodies containing a token. Inspect only status and safe `success`/`message` fields.

## Common Local Procedures

**Browser-only Admin/Staff competing-login attempt:** `POST /api/admin_app_api.php` with JSON `{ "action": "login", "username_email": "<target account>", "password": "<typed locally>" }`. This endpoint is in the active code and uses the same active-device claim. If using DevTools Console, print only `status`, `success`, and `message`, never the full JSON response. The endpoint URL is `http://localhost/loyalty_managements/api/admin_app_api.php`.

**CSRF variants:** First perform the normal UI action (valid token). Then, only against a disposable local fixture, replay the same request from DevTools Network after removing `X-CSRF-Token`/`csrf_token`; repeat with a deliberately altered token. Expect HTTP 403 and no database-side change. Verify the same user remains logged in by refreshing their dashboard. Do not share the token value.

**Cookie inspection:** Browser DevTools → Application/Storage → Cookies → `http://localhost`. Inspect flags only; do not reveal values. The active source defines portal JWT cookies `jwt_token_customer`, `jwt_token_rider`, `jwt_token_staff` (Admin and Staff share the staff cookie) plus `lm_device`. Expected: JWT and device cookies are `HttpOnly`, `SameSite=Lax`; `Secure` is false on plain HTTP localhost and true on HTTPS production. A Secure cookie is not expected to be sent over local HTTP. `HttpOnly` means page JavaScript cannot read it; `SameSite=Lax` still permits ordinary top-level navigation.
